# Sentinel AML — Application Context

## What it is
A web-based Anti-Money Laundering (AML) investigation platform for financial analysts. It surfaces suspicious transaction alerts generated by backend detection rules, lets analysts triage them, and tracks investigation cases through to resolution.

---

## Who uses it
| Role | What they can do |
|------|-----------------|
| `ANALYST` | View and act on alerts, view cases, view customer/account detail |
| `SUPERVISOR` | Everything ANALYST can do + assign cases, close cases |
| `ADMIN` | Everything + configure detection rules, manage data ingestion jobs |

---

## Tech stack
- **Frontend:** React 19 (JavaScript), Tailwind CSS v3, react-router-dom v6, axios
- **Auth:** JWT in memory (React context) — not localStorage. Attached via `Authorization: Bearer` header on every request.
- **API:** REST, base URL via `REACT_APP_API_URL` env var, proxied to `localhost:8080` in local dev.
- **Backend enforces:** RBAC, JWT validation, PII masking — the UI trusts the API responses.

---

## Application flow
1. Unauthenticated users always land on `/login`.
2. After login the JWT is decoded client-side to extract `role`; stored in `AuthContext`.
3. All routes except `/login` are behind `ProtectedRoute` (redirects to `/login` if no token).
4. `/rules` and `/jobs` are additionally behind `AdminRoute` (redirects non-admins to `/alerts`).
5. A 401 from any API call clears the token and redirects to `/login`.

---

## Pages
| Route | Purpose |
|-------|---------|
| `/login` | Credential form → POST `/auth/login` → JWT |
| `/alerts` | Primary workspace — paginated table of alerts with filters and inline actions |
| `/alerts/:id` | Two-column detail: summary + evidence transactions, customer/account strip, audit trail |
| `/cases` | Paginated list of investigation cases with filters |
| `/cases/:id` | Two-column detail: case info + linked alerts, audit trail, close-case action |
| `/customers/:id` | Full PII, linked accounts table, recent alerts |
| `/accounts/:id` | Account fields, paginated transactions (last 30 days), active alerts |
| `/rules` | Toggle rules on/off, edit risk weight and JSON parameters |
| `/jobs` | Upload CSV files for bulk ingestion, monitor job progress with auto-poll |

---

## Key design decisions
- **No dashboard home page** — analysts land directly on the alert queue, which is the primary work surface.
- **JWT in memory only** — survives the session but not a page refresh; trade-off accepted for simplicity and XSS resistance.
- **Masking is server-side** — customer names arrive pre-masked from the API; the UI renders them as-is.
- **Role enforcement is at the API layer** — the UI hides or redirects for UX, but the backend is the source of truth for access control.
- **All pages lazy-loaded** — each page is a separate JS chunk; the main bundle stays small.
- **GlobalErrorBanner** catches all unhandled API errors via the axios response interceptor and displays them as a dismissible top banner.

## Shared components
| Component | Purpose |
|-----------|---------|
| `RiskScoreBadge` | Colored pill: 0–39 green, 40–69 amber, 70–100 red |
| `StatusChip` | Colored text chip for alert status, case status, or priority |
| `PaginatedTable` | Reusable sortable table with 25/50/100 page-size selector |
| `ConfirmModal` | Overlay confirmation dialog; dismiss variant includes a reason textarea |
| `AuditTimeline` | Collapsible timeline of status changes with actor and timestamps |
| `GlobalErrorBanner` | Fixed top banner fed by axios interceptor errors |
| `Navbar` | Top nav with role-filtered links and logout |
| `ProtectedRoute` | Redirects to `/login` if no token |
| `AdminRoute` | Redirects non-admins to `/alerts` |

## Source layout
```
src/
  api/axios.js          — axios instance, request/response interceptors, tokenStore
  context/AuthContext.js — JWT + role in memory, login/logout, useAuth() hook
  components/           — shared UI components (see table above)
  pages/                — one file per route
```
